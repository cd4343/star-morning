# Phase 6 家长可控抽奖与每日努力券设计

**状态：** 已按产品方向锁定，等待书面设计检查点确认后进入实施

**范围：** 家长抽奖设置、孩子抽奖入口、免费抽奖券日限额、并发安全和回归测试

**明确不改：** 单次付费价格 15 金币、奖池权重、保底规则、奖品内容、`draw_again` 即时补抽规则

## 1. 目标与成功标准

本阶段解决两个同时存在的问题：每日固定两次让孩子觉得反馈不足；完全放开次数又会放大随机刺激和金币消耗。

采用已经确认的方案：

- 家长可把每日付费抽奖上限设置为 1–5 次。
- 每日最多使用 1 张努力券；家长可以关闭努力券入口。
- 抽中“再抽一次”属于本次中奖结果，不占付费次数，也不占努力券次数。
- 现有家庭默认保留每日 2 次，避免部署后静默扩大抽奖；家长可在设置中明确改为 5 次。
- 每次抽奖都有真实奖品，孩子看到的数值必须和实际到账一致。

验收时必须满足：家长保存 5 次后，孩子可进行最多 5 次付费抽奖，并可额外使用 1 张努力券；并发连点不能突破任一上限。

## 2. 方案比较

### 方案 A：5 次付费上限 + 1 张每日努力券（采用）

兼顾可玩性、家长控制和确定性。最大日金币成本清楚可见：`5 × 15 = 75` 金币；努力券是额外的一次行为奖励。

### 方案 B：付费与努力券合计最多 5 次

安全边界最紧，但孩子拿到努力券后可能只是替代原有付费次数，努力行为的额外反馈不明显。

### 方案 C：只把付费次数改为 1–5，不设努力券

实现最简单，但无法形成“完成行为得到一次额外机会”的短反馈闭环。

## 3. 业务规则

### 3.1 家长设置

沿用 `/api/parent/lottery-settings`，不新增一级导航。设置项放在现有奖池管理页的“抽奖安全设置”卡片：

1. 抽奖总开关。
2. 每日付费次数：离散选项 1、2、3、4、5。
3. 每日努力券：开启时上限为 1，关闭时为 0。
4. 影响预览：显示“最多消耗 N 金币 + 1 张努力券”。

关闭抽奖时，付费抽奖、努力券和“再抽一次”全部不可继续，但不能把已配置的 5 次重置回 2 次；重新开启后恢复此前设置值。设置接口始终返回配置值，孩子接口在关闭时把实际剩余额度返回为 0。

### 3.2 孩子抽奖顺序

服务端是唯一判定来源：

1. 若今天尚可使用努力券且背包有可用券，优先消耗最早获得的一张。
2. 否则，若仍有付费次数，按固定 15 金币抽奖。
3. 两种额度都用尽后拒绝抽奖。
4. `draw_again` 继续走现有 `/api/child/lottery/redraw`，不占上述额度。

`lottery_ticket` 与奖品效果 `free_spin` 都归入“努力券”日限额，避免通过不同券来源绕过限制。历史库存不清空，未使用的券继续留在背包，下一天可再使用。

### 3.3 孩子端反馈

中心按钮根据下一次真实支付方式显示：

- 有可用努力券：`使用努力券`，副文案 `今日 0/1`。
- 走付费抽奖：`抽一次`，副文案 `15 金币`。
- 全部用尽：`今天已完成`，说明明天北京时间 0 点重置。
- 家长关闭：沿用“家长已关闭抽奖”。

不能再出现“按钮写明天再来，但背包里的券实际还能抽”的冲突状态。底部状态同时显示“付费 X/N”和“努力券 X/1”，不把两种额度混成一个数字。

所有本批新增的用户可见文案进入现有 i18n 语言包，通过 `t('key')` 使用，不在组件中新增硬编码中文。

## 4. 数据与迁移

现有 `family_lottery_settings.daily_paid_limit` 带有 `0–2` 的 CHECK，不能原地扩大。遵循只追加迁移：

- 给 `family_lottery_settings` 追加 `paid_draw_limit_v2 INTEGER DEFAULT 2`。
- 追加 `daily_ticket_limit INTEGER DEFAULT 1`。
- 保留旧 `daily_paid_limit`，新逻辑优先读取 `paid_draw_limit_v2`。
- 用 `PRAGMA table_info` 检查后再 `ALTER TABLE ADD COLUMN`，迁移可重复执行。

新增 `lottery_ticket_daily_usage`：

- `id TEXT PRIMARY KEY`
- `family_id TEXT NOT NULL`
- `child_id TEXT NOT NULL`
- `usage_date TEXT NOT NULL`，写入北京时间业务日期 `YYYY-MM-DD`
- `inventory_id TEXT NOT NULL`
- `used_at TEXT NOT NULL`
- `UNIQUE(child_id, usage_date)`，从数据库层阻止当天重复使用
- 索引 `(family_id, usage_date)`

券扣减、日使用记录写入和抽奖结算必须在同一事务中；任一步失败全部回滚。多张合并券只扣 1 张，剩余数量继续保留。

## 5. 接口兼容

### 家长设置

`GET /api/parent/lottery-settings` 返回：

```json
{
  "enabled": true,
  "dailyPaidLimit": 5,
  "dailyTicketLimit": 1
}
```

`PUT /api/parent/lottery-settings` 支持原子保存三项设置；`dailyPaidLimit` 只允许 1–5，`dailyTicketLimit` 只允许 0 或 1。旧客户端只传 `enabled` 时保留已有次数设置。

### 孩子信息

`GET /api/child/lottery/info` 保留 `dailyLimit`、`remainingDraws` 等旧字段，并增加：

- `dailyPaidLimit`
- `todayPaidDrawCount`
- `remainingPaidDraws`
- `dailyTicketLimit`
- `todayTicketDrawCount`
- `remainingTicketDraws`
- `availableTicketCount`
- `nextDrawMode: "ticket" | "coins" | "none"`

抽奖结果接口返回更新后的同一组额度，前端不依赖本地背包推断是否还能抽。

## 6. 错误与安全

- 家庭设置只能由 `parent` 角色修改，并按 `familyId` 隔离。
- 每日额度在事务开始后、扣币或扣券前再次读取。
- 两次并发请求最多一笔成功消耗当天努力券。
- 金币不足、次数用尽、家长关闭、奖池无效均返回明确 4xx 信息。
- 日期重置使用北京时间工具，不依赖服务器时区或 SQLite `localtime`。
- 不写入或替换 `stellar.db`；由后端启动迁移补齐结构。

## 7. 测试意图

后端至少覆盖：

1. 旧家庭迁移后仍为 2 次，设置 1–5 均可保存，0/6/小数被拒绝。
2. 家庭设置隔离，孩子不能修改。
3. 第 5 次付费成功，第 6 次在扣币前失败。
4. 付费额度用尽后仍可使用当天第 1 张努力券，第 2 张不能使用。
5. 两个并发努力券请求只有一个成功。
6. 合并库存只扣一张，失败事务不丢券。
7. 北京时间跨日后额度重置。
8. `draw_again` 不占付费和努力券额度，且不能伪造或重复消费。

前端在 375px smoke 中覆盖：

1. 家长选择 5 次和开启努力券，预览最大 75 金币并保存成功。
2. 孩子按钮准确显示“使用努力券 / 15 金币 / 今天已完成”。
3. 额度变化后状态立即刷新，无“明天再来但仍可抽”的矛盾。

## 8. 发布与回滚

按后端规则、家长设置、孩子反馈、回归测试分独立提交。全部验证通过后生成新的时间戳增量包；不修改历史 `临时/` 包，不包含数据库文件。

回滚只恢复本批次代码文件。新增列与使用记录表保留但旧代码不会读取，不需要破坏性数据库回滚。
