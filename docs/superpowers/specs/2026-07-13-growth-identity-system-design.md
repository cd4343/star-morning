# Phase 4 统一成长身份系统设计

状态：待产品确认

范围：系统成就名称与图标、个人等级、称号、轻量装扮、历史数据兼容

不包含：新货币、付费装扮、抽卡、宠物养成、金币商店装扮、等级功能门槛，以及本阶段无关的成就条件、阈值和奖励数值调整

## 1. 目标

Phase 4 要让孩子一眼看懂“我完成了什么、我成长到哪里、我可以怎样展示自己”，同时不增加新的经济账本。

成功标准：

- 所有系统成就名称全局唯一，同名不再表示不同条件。
- 系统图标在不同设备上保持一致，同一视觉含义不被滥用。
- 成长经验只决定个人等级；特权点仍是非商品权益账本；金币仍只用于商品。
- 等级不锁定现有核心功能，只解锁展示型装扮。
- 家长自定义成就不被强制改名，既有解锁、领奖、礼包和流水关系不丢失。
- 家长端与孩子端使用同一份服务端展示结果，不再各自推导名称。

## 2. 现状与冲突

当前 `achievement_defs.title` 中已有部分分类专属名称，但 `backend/src/server.ts` 和 `frontend/src/utils/achievementDisplay.ts` 又分别按条件与等级生成 `displayTitle`。例如生活、学习、运动的连续三天成就最终都被映射为“三日成习”。两套映射还可能随版本漂移。

当前等级采用 `floor(xp / 100) + 1`，这一口径已经被后端、孩子端和成就条件引用。`levelPerks.ts` 同时展示“背包转赠权、抽奖资格”等功能权益和未实现预告，容易让孩子误以为等级决定使用权限。

当前 `users.avatar` 只保存字符，没有头像框、主题、称号选择和装扮解锁记录。

## 3. 方案选择

### 方案 A：稳定系统键 + 统一目录（采用）

每个系统成就拥有稳定 `systemKey`，名称、说明、图标键和分类来自唯一的服务端目录。API直接返回最终展示字段，前端不再二次改名。家长自定义成就仍使用原始字段。

优点：名称可安全升级，前后端一致，历史关系不依赖文案。缺点：需要一次幂等回填和目录测试。

### 方案 B：只批量修改数据库标题

改动少，但无法解决后端、前端重复映射和未来再次漂移，因此不采用。

### 方案 C：继续由前端按等级自动取主题名

无需迁移，但多维成就必然再次撞名，家长端和孩子端也容易不一致，因此不采用。

## 5. 图标系统

### 5.1 技术形态

系统成就不再依赖数据库中的Emoji作为主图标。目录保存稳定 `iconKey`，前端通过一个集中式 `GrowthIcon` 组件渲染 Lucide 或本地简洁SVG；旧 `icon` 字段只作为降级显示。

每个成就图标由三层组成：

1. 分类底色：说明成长方向。
2. 主符号：说明具体行为。
3. 里程碑环：说明该系列进度，而不是另一种货币等级。

## 6. 个人等级体系

### 6.1 定位

等级是不可消费的长期成长记录，只由成长经验 `xp` 决定。Phase 4 保留现有每100经验一级的算法，避免既有孩子等级倒退或跳变。

特权点继续由 `rewardXpTotal` 的阶段累计产生，和等级分账。金币、成长经验、特权点三者不互换。

### 6.2 六段成长身份

| 等级 | 阶段称号 | 表达含义 | 默认头像框 |
| --- | --- | --- | --- |
| Lv.1–3 | 启程星芽 | 愿意开始就是第一步 | 星芽框 |
| Lv.4–7 | 稳步行动家 | 能把小步骤继续做下去 | 晨光框 |
| Lv.8–12 | 自主探索者 | 开始选择并安排自己的行动 | 罗盘框 |
| Lv.13–18 | 习惯建造师 | 逐渐形成稳定节奏 | 积木框 |
| Lv.19–25 | 成长领航员 | 能复盘、计划和帮助家人 | 星轨框 |
| Lv.26以上 | 星河开拓者 | 持续探索自己的成长方向 | 星河框 |

中间等级显示“阶段称号 · Lv.N”，不再拼接罗马数字。升级弹窗只显示新等级、距离下一步和新获得的展示装扮，不宣称解锁抽奖、转赠等核心功能。

## 7. 轻量装扮体系

### 7.1 首版范围

- 头像：保留现有家庭成员头像，并增加一组中性星星角色头像。
- 头像框：由六段等级身份解锁。
- 个人卡片主题：生活、学习、运动、活动、探索五类主题。
- 展示称号：等级阶段称号与已解锁的精选成就称号。
- 成就徽章位：个人页最多选择3枚已解锁成就展示。

装扮不进入金币商店、不参与抽奖、不新增装扮币，也不改变任务、审核、抽奖或探索权限。

### 7.2 解锁来源

- 等级阶段：头像框。
- 指定系统成就：分类卡片主题或称号。
- 探索里程碑：探索主题和徽章。
- 家庭纪念：预留人工授予来源，但首版不提供上传自定义素材。

### 7.3 数据模型

新增表均为幂等追加，不修改 `stellar.db` 文件：

- `user_cosmetic_unlocks(child_id, cosmetic_key, source_type, source_key, unlocked_at)`，唯一键为 `(child_id, cosmetic_key)`。
- `user_profile_customization(child_id, avatar_key, frame_key, theme_key, title_key, featured_achievement_ids, updated_at)`，每个孩子一行。

装扮目录保存在代码中，用户选择接口必须验证装扮已解锁且属于本人家庭。无效或已下架装扮自动回退默认样式，不删除历史解锁记录。

## 8. 成就身份与历史兼容

`achievement_defs` 追加 `systemKey TEXT` 和 `isSystem INTEGER DEFAULT 0`。新家庭的系统成就直接写入稳定键。

老家庭回填时使用“条件类型 + 条件值 + 条件分类 + 已知旧标题集合”识别系统成就。只有满足已知系统特征的记录才标记为系统成就；家长改过名称或自行创建的记录保持自定义。

系统成就API通过 `systemKey` 返回目录中的 `displayTitleKey`、`displayDescriptionKey` 和 `iconKey`。数据库原始标题保留作为历史快照，不作为关联键。`user_achievements.achievementId`、领奖时间、礼包ID和奖励流水均不改变。

## 9. 页面与交互

孩子端“成长/我的”采用四层结构：

1. 当前身份卡：头像、头像框、阶段称号、等级进度。
2. 一个主行动：“去看看新解锁的装扮”或“继续今天的行动”。
3. 成就分类与最近点亮。
4. 折叠后的完整成就馆和装扮柜。

家长端成就管理显示“系统成就/家庭自定义”标记。系统成就允许调整奖励和发放方式，但名称、条件和图标由系统目录管理；需要个性化时可复制为家庭自定义成就。

所有新增用户可见字符串必须使用 `t('key')`；375px宽度下不横向滚动，不依赖hover。

## 10. API边界

- `GET /api/child/growth-identity`：等级身份、经验进度、可用与已选装扮、精选成就。
- `PUT /api/child/profile-customization`：仅更新本人已解锁装扮。
- 现有成就接口继续返回兼容字段，同时增加 `systemKey`、`iconKey` 和最终展示字段。
- 家长端系统成就编辑接口拒绝修改系统身份字段，但允许修改奖励字段。

接口继续使用JWT角色校验，路径保持kebab-case，错误使用统一响应格式。

## 11. 测试与发布

- 目录测试：系统键、中文名称和图标键全局唯一；每项都有i18n文案。
- 显示测试：同一档位不同分类不会出现相同名称；家长端和孩子端返回一致。
- 迁移测试：重复启动幂等；自定义成就不变；既有解锁与礼包关联不变。
- 等级测试：升级前后算法保持100经验一级，等级不会回退。
- 装扮测试：未解锁不可选择、跨家庭不可修改、下架资源安全回退。
- 前端测试：375px成就馆、身份卡、装扮柜；空状态、锁定态和已解锁态。
- 完成后运行后端全部测试、前后端构建、生产资源验证，并生成新的无 `dist` 累计安全上传包。

## 12. 实施批次

1. P4-1：建立系统成就目录、稳定键、唯一性测试，消除重复显示。
2. P4-2：完成老家庭幂等识别和API统一展示字段。
3. P4-3：重构等级称号、升级反馈，移除虚假功能权益暗示。
4. P4-4：新增装扮解锁与选择数据模型、接口和权限测试。
5. P4-5：完成孩子端身份卡、成就馆、装扮柜及家长端系统成就标记。
6. P4-6：全量回归、生产发布与历史数据验收。

每一批独立提交、可单独回滚；数据库只做追加迁移，不替换生产数据库。
