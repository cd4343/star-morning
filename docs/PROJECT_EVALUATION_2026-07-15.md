# Star Coin 项目现状评估与阶段路线

## 1. 审计范围

本次评估覆盖孩子核心闭环（今天 → 执行 → 审核 → 奖励 → 成长）、家长配置、商店/抽奖、成就装扮、家庭探索，以及当前前后端结构、测试和生产部署约束。

界面证据使用用户提供的部署截图；线上自动采集因站点连接超时未完成。因此本报告不声称完成全流程可访问性合规验证，父母端探索重构后的最终真机表现仍需部署后复核。

## 2. 用户目标和可访问性目标

产品的核心不是儿童任务清单，也不是游戏商城，而是让孩子更容易开始一件现实中的事、较快得到明确反馈，并让家长用较少配置维持一致规则。6–12 岁儿童界面应降低选择过载、保证主要动作清楚、在 375px 上可点击和可读。

## 3. 已确认的优势

- 产品定位已经形成差异：现实行为激励、家庭协作、成长记录和探索体验，而不是单纯打卡或地图。
- 家长端与孩子端职责分开；探索明确不发金币、不变成任务，产品边界是正确的。
- 奖励经济已有 10 金币约等于 1 元的家庭价值锚点，金币、成长经验和权益点职责已拆开。
- “今天”已形成低门槛入口，成长身份、成就和装扮开始从奖励堆叠转向长期记录。
- React 18、TypeScript、Vite、Express、SQLite 是清晰且成熟的现有技术组合，足以支撑单家庭或小规模试用。
- 已有 17 个后端测试文件和 5 个前端 smoke/production 规格，关键经济、成长、探索模块已开始从无测试走向可回归。

## 4. UX 风险

### P0：随机奖励的状态表达不一致

当前孩子端在付费次数用尽时会显示“明天再来”，但只要背包存在免费券，按钮仍可能可用；同时按钮继续显示 15 金币。这会让孩子无法判断下一次到底消耗什么。Phase 6 必须优先修复。

### P1：家长配置仍然过密

商店、储蓄、抽奖、奖池、经济设置集中在 `ParentWishes.tsx`，该文件已达 2084 行。功能虽然齐全，但“配置规则”和“管理内容”混在同一页面，首次使用者很难判断先做什么。

### P1：孩子端奖励入口刺激密度偏高

抽奖视觉权重很高，且商店、背包、储蓄、权益同时存在。需要继续坚持“每个页面只有一个主行动”，并把概率、额度和消耗说清楚，避免抽奖成为产品主目标。

### P1：部分成长文案过于成人化

截图中的“两本账分开记录，不会互相扣减”等说明适合家长，不适合孩子首屏。孩子端应优先回答“我现在是什么、下一步做什么”，复杂制度放到帮助说明。

### P1：移动端信息出现截断和拥挤

成就管理截图中标题出现省略，横向分类在窄屏只露出部分文字；奖励记录卡片也有不自然换行。结构信息存在，但移动端扫读效率不够。

## 5. 可访问性风险

- 已看到多处 44px 控件和安全区适配，这是正确基础。
-  pastel 背景上的浅灰小字可能存在对比不足，需要以真机截图和自动化检查确认。
- 部分图标依赖 emoji 表意，需确认按钮有文本或可访问名称。
- 横向滚动分类必须给出明显的可滚动线索，不能让被截断项看起来像缺失。
- Toast、中奖结果和保存成功属于状态变化，需要验证屏幕阅读器可感知；当前截图只能确认视觉反馈，不能确认语义播报。

## 6. 技术与结构风险

### 6.1 超大模块正在抬高回归风险

- `backend/src/server.ts`：7849 行
- `ParentWishes.tsx`：2084 行
- `ParentDashboard.tsx`：1989 行
- `ChildChallenge.tsx`：1867 行
- `ChildWishes.tsx`：1395 行
- `ParentExplore.tsx`：1342 行

不建议进行一次性重构。后续只在修改相关功能时，把规则、路由或独立面板逐步拆出，保证每次都可回滚。

### 6.2 API 规则仍有前端重复推断

孩子抽奖能否继续目前同时依赖后端次数、本地金币和背包数据。业务资格应由后端返回结构化状态，前端只负责展示，否则容易再次出现“显示与真实行为不一致”。

### 6.3 国际化基础存在但覆盖不完整

项目已有 `i18n` 和中文语言包，但当前页面仍有大量硬编码中文。新模块应严格使用 `t('key')`，旧页面在触及时渐进迁移，不做全量替换。

### 6.4 安全与运营成熟度仍是试用级

JWT 存放在 localStorage、SQLite 单文件部署、手工增量包和有限运行监控，适合当前家庭试用，但不等于面向大量外部家庭的成熟 SaaS。公开推广前需要补认证、备份演练、结构化日志和故障告警。

### 6.5 文档存在漂移

架构文档仍以早期单体结构为主，未完整反映经济、成长身份、探索工作台等新增模块。规则文档缺失或命名不一致会增加后续改错口径的风险。

## 7. 探索模块优化方向

探索应保持“家长发现和筛选 → 孩子选择与打卡 → 家长补充确认”的流程，而不是做成地图工具。

下一轮重点：

1. 家长首页先显示“待筛选、已收藏、待回应”三个行动状态，不先展示全部地点。
2. 地点卡片首屏只保留适龄、距离/区域、预计时长、室内外和一个主操作；更多信息折叠。
3. 将筛选条件分成“今天适合什么”和“高级筛选”，降低配置压力。
4. 孩子端只呈现家长筛选后的少量候选，让孩子做有限选择。
5. 错误、空状态和推荐失败必须有重试或手动添加路径，不能用空数据伪装成功。

## 8. 阶段优先级与目标

### Phase 6：家长可控抽奖与努力券（当前）

目标：家长可设置每日 1–5 次付费抽奖；每天最多使用 1 张努力券；孩子始终知道下一次消耗和剩余额度。验收以并发安全、北京时间重置、375px smoke 和新增量包为准。

### Phase 7：家长一键配置与渐进式管理

目标：把“首次配置”和“日常维护”分开。提供一套推荐预设，再允许进入高级设置；不新增一级导航，不自动修改历史商品或任务。

### Phase 8：可靠性与家庭数据安全

目标：完成 httpOnly cookie 迁移方案、CSRF 防护、备份/恢复演练、结构化日志、关键接口速率限制回归和媒体隐私检查。公开邀请更多家庭前必须完成。

### Phase 9：移动端发布准备

目标：系统性验证 375px、iOS 安全区、软键盘、上传压缩与 EXIF 清理、Safari 语音兼容；然后再评估 Capacitor 封装，不提前维护多套原生客户端。

### Phase 10：效果验证而非功能堆叠

目标：只记录家庭可理解的指标，例如开始任务所需时间、完成后反馈等待时长、每周主动选择次数和探索回顾，不做儿童实时定位或高侵入行为追踪。

## 9. 下一步决策

先完成 Phase 6，不同时添加电子宠物、新货币或新导航。Phase 6 上线并观察一周后，再进入 Phase 7 的“一键配置 + 高级设置”设计，以真实使用反馈决定是否继续增加功能。
