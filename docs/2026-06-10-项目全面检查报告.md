# Star Coin 项目全面检查报告

**日期**：2026-06-10
**方式**：5 个维度并行只读审计（后端安全、后端业务逻辑、前端代码质量、孩子端 ADHD 体验、项目卫生），未修改任何文件。最严重的 4 项发现已逐行交叉验证属实。
**范围**：backend/src 全部（server.ts 7431 行分段精读）、frontend/src 57 个文件、git 状态、临时/ 增量包、docs/、依赖。

---

## 总体结论

这个项目比你自己评价的要好。底子是健康的：SQL 全部参数化（零注入点）、家庭数据隔离完整（无越权路由）、孩子端文案是全应用最强的部分（真正消化了 ADHD 原则，不是贴标签）、抽奖保底设计是教科书级的。

真正的问题集中在四个方面，按危险程度排序：

1. **部署链路断裂**——三天的关键安全修复只存在于你本地未提交的代码里，生产服务器还在跑没有这些修复的旧版本。
2. **账目正确性**——批量审核有一个会无限刷特权点的公式错误，自动审批可重复发币，余额扣减可并发扣成负数。
3. **孩子反馈闭环断裂**——任务被打回时孩子得不到任何原因和通知；这直接违背产品初衷，是产品层面的最大伤害。
4. **长期债务**——i18n 零起步、217 处 any、时区三套口径并存、文档与代码漂移。

## 一、高危问题（建议一周内处理）

### H1. 三天的安全修复未提交、未部署，生产环境处于已知不安全状态

- **位置**：整个工作区。57 个文件改动（+10301/-9290 行）未提交，最后提交停在 6-07；main 还领先远程 4 个提交未推送。
- **影响**：双重风险。(a) 机器故障即丢失三天工作，其中包括 JWT_SECRET 强制校验、CORS 生产收紧、上传配额等安全修复；(b) 生产服务器跑的是 6-08 增量包，**没有这些修复**——线上 JWT_SECRET 缺失时只 warn 不拒启，CORS 仍宽松。
- **修复方向**：今天就做：按功能分批提交 → push → 打新增量包部署。这是所有修复的前置条件。
- **附带确认项**：6-08 补丁中 server.ts 两处 `decodeQueryText()` 在主库被改回了 `String(value||'')`（约 160/170 行附近）。如果那是修中文 query 乱码的 fix，主库可能误回退了它——部署前请人工确认。

### H2. 批量审核的特权点公式错误，可无限刷特权点（已逐行验证）

- **位置**：`server.ts:6985-6988`（批量审核）。
- **细节**：单条审核（2554-2556）和自动审批（1774-1776）用的是正确公式 `floor(新账本/100) - floor(旧账本/100)`；批量审核却写成 `floor(新账本/100) - 当前可花余额`。这是两个不同口径（正是 CLAUDE.md Rule 7 警告过的 `rewardXpTotal` 账本 vs 余额混用）。
- **影响**：孩子只要花过特权点，每次批量审核都会把花掉的点全额补回（无限刷）；反过来，孩子若有抽奖直发的 bonus 点，批量审核会倒扣。账目已可能不准，建议修复后核对一次孩子当前特权点。
- **修复方向**：改成与 `server.ts:2554-2556` 完全相同的公式，一处小改。讽刺的是 `server.ts:3226` 有个从未被调用的 `awardChildRewards()` 函数，里面就是正确公式。

### H3. 自动审批无事务、无状态守卫，并发触发重复发币（已逐行验证）

- **位置**：`server.ts:1759-1782`，由每次家长 dashboard 请求触发（1813）。
- **细节**：`UPDATE task_entries SET status='approved' WHERE id=?` 缺少 `AND status='pending'`，发币也不在事务里。家长开两个标签页或快速刷新，同一条任务的金币/经验/特权点发两次。
- **修复方向**：UPDATE 加 `AND status='pending'` 并检查 `changes===1`，整段套用已有的 `withTransaction`（database.ts:633）。

### H4. switch-user 和孩子 dashboard 把密码/PIN 的 bcrypt 哈希返回给前端（已逐行验证）

- **位置**：`server.ts:1616+1633`（switch-user：`SELECT *` 后整行 `user:u` 返回）；`server.ts:5632,5651`（child dashboard 同样模式）。
- **影响**：哈希泄漏到浏览器，可被离线爆破家长密码/PIN（孩子拿到家长 PIN 哈希 = 可能解锁家长模式）。
- **修复方向**：复用已有的 `serializeAuthMember()`（1611 行旁边就在用）或显式字段白名单。一行级别的改动。

### H5. JWT Token 永不过期（已验证）

- **位置**：`server.ts` 全部 6 处 `jwt.sign()`（1414、1461、1543、1597、1633、1661），均无 `expiresIn`。
- **影响**：Token 存 localStorage（已知风险）+ 永不过期 = 一旦泄漏永久可用。
- **修复方向**：加 `expiresIn`（建议 30d，配合快捷登录场景），到期引导重新登录。

### H6. SQLite 单连接 + 手写 BEGIN/COMMIT 无回滚，并发下事务互相污染

- **位置**：`database.ts:6,13`（全局单连接）；裸 BEGIN/COMMIT 无 try/catch ROLLBACK：`server.ts:6041-6058、6077-6083、6124-6138、6640-6645`，`rewardSystem.ts:932-950`。
- **影响**：并发请求的语句会交错进入彼此的事务；中途任一语句失败，连接永久卡在未关闭事务中，**之后所有事务请求持续失败直到重启**。这可能是你感觉"之前 AI 改完问题不少"的来源之一。
- **修复方向**：全部统一改用已有的 `withTransaction`（自带回滚），事务加进程内串行化。

### H7. 余额检查在事务外、扣减无守卫，连点可把金币扣成负数

- **位置**：抽奖 `server.ts:6234-6242`、商店 `5968-5973`、储蓄 `6121-6125`、特权 `6637-6641`；抽奖每日 10 次上限同样可并发突破（6222-6229）。
- **影响**：孩子端连点按钮即可在余额不足时连续消费、余额变负。
- **修复方向**：扣减统一改为 `UPDATE users SET coins = coins - ? WHERE id = ? AND coins >= ?` 并检查 `changes`。

### H8.（产品高危）任务被打回时，孩子得不到任何原因和通知

- **位置**：后端 `server.ts:5641-5648`（recentReviews 只查 `status='approved'`）；`ParentDashboard.tsx:696`（打回请求不带 reason 字段）。
- **影响**：孩子"做了但不知道为什么没通过"——这是 CLAUDE.md P3 明令禁止的场景，对畏难情绪是直接打击，且没有修复指引。**这一条对产品初衷的伤害超过任何代码 bug。**
- **修复方向**：打回必填一句话原因；孩子端弹卡片展示"哪里可以改 + 重做按钮"。

### H9.（数据风险）近 3 周无数据库备份，且 10 天的数据只活在 WAL 里

- **位置**：`backups/` 最新备份停在 5-18；根目录 `stellar.db` 主文件停在 5-31，而 729KB 的 `stellar.db-wal` 是 6-10 的。
- **影响**：照"单拷 stellar.db"的旧备份方式操作，会静默丢掉 WAL 里约 10 天的数据。backup.ts 的主路径（`VACUUM INTO`）是正确的，但回退路径只拷主文件不带 WAL，同样有丢数据风险（backup.ts:50-54）。
- **修复方向**：确认服务器上 backup.ts 定时任务是否在跑；回退路径改用 SQLite backup API 或失败即告警。

## 二、中等问题（建议一个月内分批处理）

### 后端

- **M1. 生产密钥守卫依赖 NODE_ENV**（`server.ts:18-24`）：漏设 `NODE_ENV=production` 就会静默使用硬编码默认密钥。改为：检测到默认密钥即拒绝启动。
- **M2. 限流可能因缺 trust proxy 失效**（`server.ts:42-59`）：部署在反向代理后但未 `app.set('trust proxy')`，所有用户共用同一限流桶。确认部署拓扑后配置。
- **M3. 上传 MIME 只信客户端声明**（`server.ts:221-271`）：未校验 magic bytes。缓解因素：白名单无 SVG、文件名随机 UUID。建议引入 file-type 校验。
- **M4. 时区三套口径并存（约 30 处）**：UTC（如探索同日打卡判重 `server.ts:5144`——北京时间 0-8 点打卡会算到前一天）、SQLite localtime（`server.ts:7306,7312`、`rewardSystem.ts:846`，违反项目约定）、正确的 `+8 hours` 混用。周/月统计普遍偏移 8 小时。统一为 `date(col,'+8 hours')` 配对或 Node 侧算边界。
- **M5. 惩罚/调整用绝对值 SET coins**（`server.ts:7089-7106、6856-6878`）：与并发审批的相对增量更新冲突时，奖励会被覆盖凭空消失。改守卫式相对扣减。
- **M6. 三种奖励"只发不兑现"**：免费抽奖券、下次双倍、宝箱抽奖券（`rewardSystem.ts:1390-1404`、`server.ts:5837`）——孩子兑现后无任何实际效果。直接违反 P3"不能做了不知道得到什么"。要么实现，要么下架。
- **M7. 审批口径不一致**：审核建议金额与不带 finalCoins 直接通过的实发金额可能不同（`rewardSystem.ts:628-822` vs `server.ts:2502-2511`）；自动审批不应用全家任务 1.5×/1.3× 加成（1752 vs 2517）。孩子收到与预告不符的奖励。
- **M8. 异步路由大量无 try/catch + unhandledRejection 即退出进程**（`server.ts:7423-7426`）：单次 DB 报错（如 SQLITE_BUSY）= 全服务重启。加 asyncHandler 包装器。
- **M9. reward-pools PUT 无校验**（`rewardSystem.ts:585-593`）：部分更新会把其他字段写成 NULL。
- **M10. 自动审批不写 reviewedAt**（`server.ts:1759-1762`）：金币静默到账，孩子不知道哪个任务通过了——奖励与行为脱钩，强化效果归零。

### 前端

- **M11. i18n 基础设施完全不存在**：无任何 i18n 依赖、无 t() 函数，约 3563 行硬编码中文（占代码 16%），连最新探索模块也是硬编码。CLAUDE.md Rule 2 的 i18n 约定目前无法被任何新代码遵守。先搭最小骨架（只有 zh 也行），新代码强制走 key。
- **M12. any 共 217 处、API 响应全部无类型**：重灾区 ChildWishes.tsx（33 处，1406 行零 interface）。后端字段改名前端编译期完全无感知——`accumulatedRewardXp`→`rewardXpTotal` 这类历史事故还会重演。以 `types/explore.ts`（做得对的范例）为模板逐步补。
- **M13. 质量门禁失效**：`.eslintrc.cjs` 规则为空 + tsconfig 关闭未用检查，46 处死导入/死函数无人拦截。
- **M14. Toast Provider 未 memo 引发"弹 toast → 全局重渲染 → 重复请求"**（`Toast.tsx:114` + `ChildLayout.tsx:27-93`）：每次 toast 出现/消失，孩子端额外发一次 dashboard 请求。一行 useMemo 修复。
- **M15. 防息屏视频依赖 GitHub CDN**（`ChildTasks.tsx:385`）：国内基本不可达，iOS 上兜底静默失效，任务计时中熄屏。把静音视频放进 public/ 本地引用，5 分钟修复。
- **M16. 8 处静默吞错，关键一处**：孩子点"我卡住了"失败被 `catch {}` 吞掉（`ChildChallenge.tsx:787`）——求助信号可能丢失且无提示。
- **M17. react-router 6.x 开放重定向漏洞**（GHSA-2j2x-hqr9-3h42，moderate，有 fix）：面向家长/儿童的登录应用，可被钓鱼利用。`npm audit fix` 后回归。

- **M18. 顶栏信息过载**（`ChildLayout.tsx:155-222`）：两套货币 + 两条进度条 + 换算公式常驻。只留金币+等级，其余折叠。

## 三、建议项（有空再做）

- 升级庆祝缺失：每 100 XP 升级无任何动画——成本最低的自信强化时刻被浪费了。挑战页/学习提交的反馈强度也弱于旧页。
- 保底触发但奖池无稀有奖品时仍报告"保底触发"，孩子看到保底却开出普通奖（`rewardSystem.ts:1296-1317`）。

- `finalCoins` 无范围校验，家长端可传负数（`server.ts:2507`）。
- 死代码清理：`awardChildRewards`（修 H2 时顺手启用它最好）、`useApiCall.ts` 整文件、`getLotteryCostV2` 旧费用曲线、46 处未用导入。
- 宝箱设置接口静默忽略家长输入，只有 isEnabled 真正生效（`rewardSystem.ts:235-320`）。
- 认证页还在用 `alert()/confirm()`（8+19 处），与全站 Toast 风格不一致。
- 冷静页"做到了/有帮助"两个按钮语义混淆（`ChildCalm.tsx:376-383`）。
- 孩子端大量 9-10px 字号，低于可读下限。
- 28 处 `hover:` 类改 `active:`；31 处硬编码 `'zh-CN'` locale 抽成常量。
- SMS 端点泄漏手机号是否注册（用户枚举）；全局 20MB body limit 偏大；非认证端点无限流。
- backend qs 依赖 DoS 漏洞（moderate）；前后端 axios 版本割裂。
- 提交信息执行 P1 批次编号约定（近 20 条无一条符合）；`.workbuddy/` 加入 .gitignore；两个 debug.log 可删。
- B3-5 审核通知基线持久化到 localStorage，否则应用关闭期间的审核永远不触发庆祝。

## 四、产品层面缺口（对照你的初衷）

| 初衷 | 现状 | 缺口与建议 |
|---|---|---|
| 交朋友 | 仅一条默认特权模板"和朋友玩" | **完全无功能支撑，最大缺口。** 可做：社交类任务模板（打招呼/邀请同学）、探索打卡加"和谁一起去"字段 + 社交成就 |
| 愿意表达 | 探索语音留言、卡住原因选择 | 无主动表达场景。可做：完成任务后"讲给家长听"加成、语音被家长回应的闭环 |
| 更自信 | 成就 + 等级，但升级零庆祝；复盘（惩罚）与成就同权重并列 | 补升级庆祝；做"月度高光时刻"成长回顾；成就视觉权重压过复盘 |
| 更专注 | 计时器、并行限制、游戏票 | 专注数据（实际用时 vs 目标）孩子自己看不到，无法自我觉察进步 |
| 克服畏难 | **支撑最好**：勇气关、卡住四选项、3 分钟启动话术 | 基本闭环，补"勇气关连续完成"成就即可 |
| 尝试新事物 | 探索模块设计完整且克制 | 打卡确认同样缺家长提醒 |
| 积极主动 | "推荐先做"、早晨连续奖励 | 基本覆盖 |

结构性缺口：**修复型惩罚**——文档承诺"惩罚是修复机会"，代码里只有扣除，没有任何补救/赎回路径。
